为什么使用 use 这种方式来导出，感觉不符合直觉，use，一般是指当前文件使用了什么，结果却用来导出，正常应该使用 export 这种来导出，还比较符合直觉


# 先说核心痛点：你的直觉非常合理
绝大多数语言：
- JS/TS：`export` 向外暴露；`import` 引入别人的
- Go：`func Name()` 首字母大写=导出
- Python：`__all__`、顶层名字自然导出

大家习惯**两个关键字分开：导入 ←→ 导出**。
但 Rust 用同一个 `use` 同时干两件事，非常反直觉。
```rust
// 1. 普通use：拿来自己用（私有）
use std::collections::HashMap;

// 2. pub use：拿来再向外转发（重导出reexport）
pub use std::collections::HashMap;
```

## 一、先解释：Rust 语法设计上为什么没有单独的 `export`？
### 1. Rust 的命名空间模型：`use` 的本质不是“导入文件”，而是**创建本地别名绑定**
很多人误解：
> `use` = 从别的文件加载代码

❌ 错误理解。
✅ Rust 里 `use` **只作用于当前模块的符号表**：
在当前模块，给一个长路径起一个局部短名称。

```rust
use a::b::c;
```
含义：**在当前模块范围内，名字 `c` 等价于 `a::b::c`**。
仅此而已！不加载代码、不链接，只是名字映射。

那 `pub use` 只是给这条绑定**加上公开权限**：
普通 `use`：别名仅当前模块可见
`pub use`：这个别名**对外模块也可见**

逻辑链条：
`use` = 创建局部别名
`pub` = 控制这个别名能不能被外部访问

所以设计者思路：
不需要新关键字 `export`，只要给 `use` 的别名加上可见性修饰符 `pub` 就够了。

> 类比想象：
> 如果普通 `let x = y;`
> 有一个魔法版本 `pub let x = y;`，允许外部访问这个绑定。
> `pub use` 就是模块层面的“公开别名绑定”。

### 2. Rust 统一路径语法：路径表达式不分方向
不管是引用、转发，路径写法一模一样：
```rust
use tokio::task::spawn;          // 自用
pub use tokio::task::spawn;      // 转发出去
```
设计者追求：路径语法统一，不要两套语法（import path / export path）。

## 二、对比：如果设计成 `export`，会有什么问题？
假设模仿 JS，新增关键字：
```rust
// 假想语法，Rust 没有
export tokio::task::spawn;
use tokio::task::spawn;
```
问题：
1. 两套几乎一样的路径语法，增加语言复杂度；
2. 别名机制要实现两套：`use ... as` / `export ... as`；
3. 无法表达“先use本地别名，再对外导出”的连贯模型。

Rust 选择**最小关键字集合**，复用已有工具，代价就是对新手不直观。

## 三、区分两个极易混淆概念，帮你理顺直觉
### 1）模块项原生导出（不需要use）
写在模块里，直接定义的东西，靠 `pub` 控制是否对外暴露：
```rust
pub fn hello() {}   // 原生定义，pub控制导出
struct Secret;      // 默认私有
```
这是**定义层面的可见性**。

### 2）重导出 pub use（不是在这里定义，只是转发名字）
`pub use X`：**当前模块没有定义这个东西，只是转发别处已经存在的符号**。

> 分界线：
> ✅ 自己定义：`pub fn / pub struct`
> ✅ 转发别人定义好的：`pub use`

很多语言没有“转发导出”这个强力特性。
JS 也有类似能力：
```js
export { spawn } from "./task.js";
```
但 JS 专门用 `export ... from` 语法区分，所以直觉上更好接受。
Rust 选择不新增语法，复用 `use + pub`。

## 四、一个形象类比，帮你扭转直觉
想象一栋写字楼：
- `pub struct Foo`：你在本楼层新建一间办公室，标记【对外开放】
- `use a::Foo`：你在本楼层贴一张便签：“Foo = A楼层的Foo办公室”，仅供本楼层内部人看
- `pub use a::Foo`：你把这张便签贴到楼层导视牌上，**整栋楼所有人都能通过本楼层找到A楼层的Foo**

`use` 始终是“贴别名便签”；`pub` 决定便签是否对外公示。

## 五、历史小补充（Rust RFC 角度）
早期 Rust 也有人提议增加 `export` 关键字。
Rust 团队权衡后选择拒绝，核心理由：
1. `pub use` 已经可以表达所有转发需求；
2. 新增关键字会破坏语法、增加语言学习负担；
3. 可见性修饰符 `pub` 统一管理所有项（函数、结构体、use别名、模块），设计更一致。

## 六、给你一个记忆口诀，消除认知冲突
1. **普通 use**：创建别名，仅供本模块内部使用
2. **pub use**：创建别名，并且把这个别名对外开放（重导出/reexport）
3. `use` 永远是「别名绑定工具」；它本身不负责导入或者导出，**`pub` 才是控制对外可见的开关**

## 延伸思考题（结合你之前看的 Tokio）
如果 Rust 有单独的 `export` 关键字：
```rust
// 假想代码
export task::spawn;
```
功能和现在 `pub use task::spawn;` 完全等价。
只是语法观感更符合你的直觉，但语言层面多一套关键字。
