# Copy 与 Drop 互斥的底层原理
## 1. 两条核心规则
1. 一个类型**不能同时实现 `Copy` 和 `Drop`**，编译器会直接报错；
2. 只要手动实现了 `Drop trait`，该类型自动失去实现 `Copy` 的资格；
3. 内置简单类型（i32、bool、&str、数组`[T;N]`且T是Copy）自动派生Copy，它们都没有Drop。

## 2. 根本矛盾：两种所有权语义完全冲突
### 先回忆两个 trait 的含义
#### Drop：拥有独占资源，离开作用域必须清理
实现 `Drop` 的类型，代表它**独占管理一段需要手动释放的资源**：堆内存、文件句柄、socket、锁、内存映射等。
- 逻辑：这个资源只能属于**唯一所有者**；
- 离开作用域时 `drop()` 执行释放，销毁独占资源；
例：`String`、`Vec`、`File`、`Box<T>` 都实现 Drop，不能 Copy。

#### Copy：复制是“按位浅拷贝”，无独占资源
实现 `Copy` 的类型，按二进制字节完整复制一份，复制后**新旧两份完全独立、互不干扰**，不存在独占资源：
- 没有堆资源、没有句柄、没有需要释放的东西；
- 复制后两份都可以随便丢弃，无需特殊清理；
例：`u32`、`(i32, bool)`。

## 3. 如果同时实现 Copy + Drop，会发生双重释放（U.B 未定义行为）
假设 Rust 允许 `Box<i32>` 同时实现 Copy + Drop，看这段伪代码：
```rust
// 假设 Box 能 Copy
let a = Box::new(10);
let b = a; // Copy：按位复制胖指针，a 和 b 指向同一块堆内存
// 函数结束，a、b 先后离开作用域
// 第一次 drop(b)：释放堆内存
// 第二次 drop(a)：重复释放已经释放过的堆内存 → 内存崩溃
```
- `Drop` 要求：资源唯一归属，只能释放一次；
- `Copy` 行为：浅拷贝会产生**多个变量指向同一资源**；
二者行为天然冲突，会直接造成双重释放、内存损坏，属于严重内存安全问题。

### 简单概括冲突点
- Drop：我只能有一个主人，销毁时释放资源；
- Copy：可以无限复制出多个主人；
多个主人同时去释放同一份资源 = 内存安全灾难。

## 4. 为什么基础类型可以 Copy，没有 Drop
像 `i32`、`char`、`[u8;4]`：
- 全部数据存在栈上，**无堆资源、无需要释放的外部资源**；
- 拷贝只是复制栈上简单数值，不存在任何资源清理工作；
所以它们不需要 Drop，自然可以安全实现 Copy。

## 5. 特殊情况：Clone 不存在互斥
`Clone` 和 `Drop` 可以共存，因为 `clone()` 会**深拷贝**，分配一份全新独立资源：
```rust
let a = String::from("hi");
let b = a.clone(); // 堆上新开辟一块内存，两份字符串完全独立
// a、b 各自drop释放各自堆内存，不会重复释放
```
Clone 解决了 Copy 的浅拷贝缺陷，所以和 Drop 兼容。

## 6. 编译器硬性限制源码逻辑
Rust 类型系统规则：
> 如果类型实现了 `Drop`，则该类型**不自动实现 Copy**，并且你手动 `impl Copy for T` 会编译报错。

报错示例：
```rust
#[derive(Copy)]
struct Foo;

impl Drop for Foo {
    fn drop(&mut self) {}
}
```
编译错误：
```
the trait `Copy` cannot be implemented for this type; the type has a destructor
```

## 7. 补充例外：引用 &T 既是 Copy 又关联 Drop？
很多人疑惑：`&T` 实现 Copy，但被引用的 T 可以有 Drop？
关键点区分：
- `Copy` 是给**引用本身**实现的；
- `Drop` 是给**拥有资源的所有权类型**实现的；
引用只是借用，**不拥有资源、不负责释放资源**，引用本身没有 Drop 逻辑，不存在冲突。

## 总结一句话
`Drop` 代表类型独占资源、只能有一个所有者；`Copy` 是浅拷贝产生多份指向同一资源的变量，二者组合会导致双重释放内存安全漏洞，因此 Rust 类型系统强制互斥。
