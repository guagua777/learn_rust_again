## 为什么线程使用 `JoinHandle` 来表示？

### 核心原因

在 Rust 中，`thread::spawn()` 的返回值就是 `JoinHandle<T>`，它代表了一个**可等待、可管理**的线程句柄。不用 `JoinHandle` 的话，线程就"失控"了——你无法：

1. **等待线程结束**（`.join()`）
2. **获取线程的返回值**
3. **知道线程是否还活着**

### 在你的 `ThreadPool` 场景中

看 `src/lib.rs:19`：

```rust
threads: Vec<thread::JoinHandle<()>>,
```

这里使用 `Vec<JoinHandle<()>>` 而不是简单的 `Vec<thread::Thread>` 或什么都不存，原因在于：

| 能力 | 说明 |
|------|------|
| **生命周期管理** | `ThreadPool` drop 时，可以遍历 vec 并对每个 handle 调用 `.join()`，确保所有线程优雅退出 |
| **所有权清晰** | `JoinHandle` 持有对线程的所有权，Rust 的所有权系统保证线程不会被意外清理 |
| **线程不分离** | 如果 spawn 后不保存 handle，线程就"分离"了（detached），无法再 join |

### 对比：你现在代码的问题

看 `src/lib.rs:38`：

```rust
thread::spawn(f);  // 返回了 JoinHandle，但你把它丢弃了！
```

这行代码实际上创建了一个**分离线程**——返回的 `JoinHandle` 被立即丢弃，线程无法被 join。这与你 struct 中定义的 `threads: Vec<JoinHandle<()>>` 字段是矛盾的。

**正确做法**应该是：

```rust
// 在 execute 中，把 spawn 返回的 handle push 到 threads 里
// 但实际上对于线程池，更常见的设计是：
// 1. new() 时预先 spawn N 个工作线程，把它们的 handle 存入 threads
// 2. execute() 通过通道发送任务，工作线程从通道接收并执行
```

### 总结

`JoinHandle` 是 Rust 中**线程的所有权和控制句柄**，就像文件描述符之于文件、进程 ID 之于进程。保存它才能真正"拥有"并管理那个线程。你的 struct 定义了这个字段是正确的设计意图，接下来需要完善 `new()` 和 `execute()` 来实际使用它。

## `thread::Thread` 是什么？

`thread::Thread` 是一个**轻量级的、共享的线程引用**（类似"身份证"），它**不拥有**线程，只是一个可以克隆、可以传递的引用句柄。

### 类比理解

| 概念 | 类比 | 能否让线程停下来？ | 能否拿到返回值？ |
|------|------|-------------------|-----------------|
| `JoinHandle<T>` | 遥控器（拥有控制权） | ✅ `.join()` 可以等待 | ✅ `.join()` 返回 `Result<T, _>` |
| `Thread` | 身份证（只有标识） | ❌ 不能 join | ❌ 不能获取返回值 |

### 获取 `Thread` 的方式

```rust
// 方式1：通过 JoinHandle 获取
let handle = thread::spawn(|| {});
let thread: &Thread = handle.thread();  // 拿到 &Thread 引用

// 方式2：当前线程
let current: Thread = thread::current();  // 获取当前线程的 Thread 句柄

// 方式3：Builder 模式
let (handle, thread_ref) = thread::Builder::new()
    .name("worker".into())
    .spawn(|| {})
    .map(|h| (h.thread().clone(), h))  // 这里 clone() 出 Thread
    .unwrap();
```

### `Thread` 能做什么？

`Thread` 只能做**信息查询和简单控制**：

```rust
let t: Thread = thread::current();

t.id();           // 获取线程 ID
t.name();         // 获取线程名称（如果设置了）
t.unpark();       // 唤醒被 park 的线程（注意：park/unpark 是协作式的）
```

**注意**：`Thread` 不能 `join()`，不能让你等待线程结束，也不能拿到线程的返回值。

### 两者关系图示

```
thread::spawn(|| 42)
    │
    └──→ 返回 JoinHandle<i32>
              │
              ├── .join() → Result<i32, Box<dyn Any>> (等待 + 获取返回值)
              ├── .thread() → &Thread (拿到"身份证")
              │                  │
              │                  ├── .id()
              │                  ├── .name()
              │                  └── .unpark()
              │
              └── 当 JoinHandle 被 drop 时，线程分离（detached），无法再 join
```

### 为什么有两个类型？

这是 Rust **所有权模型**的精巧设计：

- **`JoinHandle` 是独占所有权**：一个线程只有一个 JoinHandle，谁持有它谁就能决定是否等待线程结束
- **`Thread` 是共享引用**：可以有多个 Thread 引用同一个线程，大家都能"识别"它，但没人能"终结"它

### 回到你的代码

在 `src/lib.rs:19` 中用 `Vec<JoinHandle<()>>` 是正确的，因为：
- 你希望 `ThreadPool` **拥有**这些线程
- 在 `ThreadPool` 销毁时能 `.join()` 等待它们优雅退出

如果换成 `Vec<Thread>`，你就**失去了 join 的能力**，线程池就无法保证线程的生命周期管理了。

---

**一句话总结**：`JoinHandle` = 线程的**所有权+控制权**，`Thread` = 线程的**身份标识**。你需要保存 `JoinHandle` 才能真正"管理"线程。
