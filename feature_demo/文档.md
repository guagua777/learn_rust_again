那 Cargo.toml 里的 features 是怎么串起来的？
翻一下我们当前的文件：


serde = { version = "1.0", optional = true, features = ["derive"] }
这里 features = ["derive"] — 意思是：编译 serde 时，顺便把它的 derive 功能打开。
serde 的 derive 功能本质上就是拉取 serde_derive 这个 proc-macro 包，让你能写 #[derive(Serialize)]。
所以 features = ["derive"] 等价于：


// 你不用手动加 serde_derive 依赖，serde 帮你牵线搭桥了
那之前的 json = ["serde/json"] 为什么是错的？
因为 serde/json 意思是 "把 serde 包的 json 功能启用"，但 serde 核心包里根本没有 json 功能。JSON 支持是单独的 serde_json 包，不藏在 serde 内部。

就像：你不能说"打开汽车的音响功能"如果车里根本没装音响 — 音响是另一回事，得单独加。

这样理解了吗？
简单记忆法：

serde + derive = 获得 #[Serialize] 注解能力
serde_json = 获得 JSON 格式的序列化/反序列化能力
缺了 derive，你得手写 Serialize 的 trait 实现（很麻烦）。缺了 serde_json，你只是有了序列化的接口，但没法序列化成 JSON。

有任何不清楚的点我再细讲！




## 目录结构安排（推荐，直接照抄搭建）
```
workspace/
├── feature_demo/      # 库项目（之前创建的lib）
│   ├── Cargo.toml
│   └── src/lib.rs
└── consumer/          # 二进制调用项目（新建）
│   ├── Cargo.toml
│   └── src/main.rs
```

### 操作步骤
1. 先进入 **`feature_demo 的同级目录`**（也就是外层 `workspace` 文件夹）
```bash
# 假设你现在在 feature_demo 内部，先退出去
cd ..

# 此时当前目录下能看到 feature_demo 文件夹
ls
# 输出：feature_demo
```

2. 在这个层级新建 consumer
```bash
cargo new consumer
```

此时路径关系：
- consumer 目录：`./consumer/`
- feature_demo 目录：`./feature_demo/`

所以 consumer 的 Cargo.toml 里路径 `path = "../feature_demo"` **完全正确**。

## 验证路径是否有效
进入 consumer 目录
```bash
cd consumer
cargo check
```
Cargo 会自动向上寻找 `../feature_demo` 作为依赖。

## 可选：把两者放进一个 Workspace（工程化推荐）
在外层 `workspace` 创建 Cargo.toml
```toml
[workspace]
members = [
    "feature_demo",
    "consumer"
]
```
好处：
- 统一共享 target 目录，减少重复编译
- 在外层可以一次性批量构建所有包
- IDE 识别整个工程

## 常见踩坑提醒
❌ 不要在 `feature_demo` 文件夹内部创建 consumer
如果建在里面，路径就要改成 `path = "./"`，层级会混乱，不推荐。

✅ 标准：**库和使用者项目平级**。
